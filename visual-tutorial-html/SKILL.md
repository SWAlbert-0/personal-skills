# Visual Tutorial HTML

把原始资料转化为一份可阅读、可操作、可验证的 HTML 学习教程，而不只是把文字搬进网页。

默认交付一个可直接双击打开的单文件 `.html`：内置 CSS、JavaScript、SVG 图解和完整代码，无需联网或构建工具。除非用户另有要求，不额外创建项目脚手架、依赖文件或配套文档。

## 一、核心目标

教程应同时回答四个问题：

1. **我要学什么或完成什么？** 明确学习目标；若原资料明确提出任务交付要求，再说明交付物与验收标准。
2. **为什么这样做？** 解释概念、因果关系和设计取舍。
3. **具体怎样做？** 提供分步操作、代码拆解和完整实现。
4. **如何确认做对了？** 给出运行、验证、排错和最终检查方法。

优先提升学习效率，不追求单纯视觉炫技。页面必须服务于理解、实践和复盘。

## 二、通用原则

- **资料优先**：先读用户提供的原始资料，显式要求不可凭经验改写。
- **学习路径优先**：按“目标 → 原理 → 拆解 → 完整实践 → 验证 → 排错”组织，而非照搬原文顺序。
- **图文互补**：图用于解释结构、流程、比较和关系；文字用于定义、原因、步骤与限制。
- **事实可复核**：统计量、命令、API、代码和输出不得编造。示意结果必须明确标注“示意”。
- **代码可运行**：讲解片段与完整代码保持一致，完整代码应经过语法检查和适当实测。
- **默认离线**：不依赖 CDN、在线字体、远程图片或前端框架。
- **响应式与可打印**：兼顾桌面、窄屏和打印/另存为 PDF。
- **匹配用户语言**：正文、注释、界面文案和最终说明使用用户主要语言。
- **适配现有项目**：若涉及代码修改，遵循项目已有结构、依赖、命名和测试方式。
- **任务内容条件化**：交付物、评分、答辩和提交说明只在原资料明确提出时出现，不根据教程模板自行添加。

### 交付物与提交内容的条件规则

先判断原始资料的性质，再决定页面是否包含任务交付信息：

1. 仅当资料明确属于课堂作业、课程实践、实验任务、项目交付或考核任务，**并且**提到提交物、交付要求、验收、评分、答辩或类似要求时，才在 HTML 中设置对应内容。
2. 若资料只是一般知识点、技术概念、项目代码、产品文档、论文或学习主题，且没有任务提交要求，页面不得出现“提交物清单、课堂评分、教师检查、现场答辩、提交前检查”等栏目或措辞。
3. 不得因为代码教程通常包含 README、测试或运行结果，就把它们表述为“需要提交的作业文件”。它们只能作为实际运行或学习所需内容介绍。
4. 页面默认的“验证与检查清单”用于确认学习或实践是否成功，不应自动改名为“提交清单”。
5. 若上下文没有提供任务性质，默认按普通学习教程处理，不虚构课程背景；只有该信息会改变主要交付方向时才询问用户。

这里限制的是**源任务的交付信息**，不影响最终向用户交付本次要求生成的 HTML 文件。

## 三、开始前确认输入

优先从上下文获取，不要为可推断的信息打断用户。

### 必需输入

- 原始资料：文件、链接、代码仓库、作业要求或用户给出的主题。
- 教程目标：考试学习、完成作业、掌握项目、入门知识点或操作指导。

### 可推断的默认值

- 受众：具备基础操作能力，但不熟悉当前主题。
- 交付：一个自包含 HTML 文件。
- 深度：覆盖完成任务所需的全部核心内容，扩展内容放在后面。
- 代码：若源任务要求完整实现，则同时提供“拆解片段 + 完整代码”。
- 视觉：根据主题确定，不套用固定模板。

只有在缺少的信息会实质改变交付方向时才询问用户，例如：必须面向零基础还是已有经验的开发者、必须使用某种框架还是允许纯 HTML。

## 四、制作流程

### 第 1 步：读取资料，建立要求清单

完整读取原始资料，提取并核对：

- 明确学习或实践目标。
- 若资料明确提出任务交付要求，提取最终交付物、提交方式和验收条件；否则跳过，不自行补充。
- 所有“必须”“禁止”“至少”“格式为”等硬约束。
- 技术栈、版本、运行环境和外部服务。
- 与资料相关的评价指标、验证方式和常见失败条件。
- 核心概念及其先后依赖关系。

将要求分为三组：

| 类型 | 含义 | 页面中的处理 |
|---|---|---|
| 必须满足 | 直接影响正确性或评分 | 在正文、完整实现和检查清单中重复闭环 |
| 需要理解 | 支撑实践的原理 | 用图解、类比和简短示例解释 |
| 可选扩展 | 有助于深入但非必需 | 放在后段，避免干扰主路径 |

不要只提炼主题。若原任务要求特定循环结构、文件格式、独立执行步骤或验证链，最终代码必须逐项满足。

### 第 2 步：定义学习成果与页面主线

用一句可检查的话描述教程完成后的能力，例如：

> 学习者能够独立运行该项目，解释关键设计，并用给定方法验证结果。

随后安排学习路径：

1. **目标与成果**：先展示最终要做什么。
2. **全局地图**：用一张图建立整体认知。
3. **必要知识**：只讲理解后续步骤所需的内容。
4. **环境与准备**：让读者能开始实践。
5. **核心拆解**：逐块解释结构、参数和原因。
6. **完整实现**：提供可复制、可下载的完整版本。
7. **运行验证**：给出真实命令和预期检查点。
8. **解释与迁移**：说明结果、限制和常见追问。
9. **排错与清单**：帮助独立完成最终验收。

根据主题调整，不必机械保留所有章节。纯知识教程可将“运行验证”替换为“例题、练习或自测”。

### 第 3 步：规划图解，而不是事后装饰

先找出仅靠文字难以表达的内容，再选择图形。

| 内容类型 | 推荐表达 |
|---|---|
| 工作流程 | 带方向的流程图、闭环图 |
| 系统结构 | 分层架构图、组件关系图 |
| 时间或步骤 | 时间线、步骤条 |
| 概念对比 | 对照卡、双栏图、表格 |
| 数据比例 | 条形图、堆叠条、矩阵 |
| 层级关系 | 树形图、嵌套图 |
| 代码执行 | 输入 → 处理 → 输出图、状态变化图 |
| 抽象知识 | 小型示意场景或关系图 |

图解要求：

- 优先使用内联 SVG、HTML 和 CSS，保证离线显示。
- 图必须有明确标题和图注，图注解释“应从中看出什么”。
- 使用真实内容标注节点，不写泛泛的 A、B、C 占位符。
- 示意图中的数字、矩阵和输出不得冒充实际实验结果。
- 不为每段文字机械配图；一张图只承担一个主要认知任务。
- SVG 提供可理解的标题或 `aria-label`，装饰图形设为 `aria-hidden="true"`。

### 第 4 步：制定主题化视觉方案

在写 CSS 前，先形成简短设计方案。

#### 色彩

定义 4–6 个语义明确的变量：

- 页面背景。
- 内容表面。
- 正文文字。
- 主题主色。
- 次要文字与分隔线。
- 成功、警告等状态色。

颜色应来自主题本身。例如，医学教程可强调清晰与冷静，历史教程可借鉴档案材质，编程实验可突出终端与证据流。不要默认套用千篇一律的“米色 + 陶土色”或“黑底 + 荧光绿”。

#### 字体

区分三种角色：

- 标题：有适度个性，用于建立主题。
- 正文：中文长文清晰易读。
- 代码与数据：等宽字体。

优先使用系统字体栈，避免联网字体导致离线失效。

#### 布局

桌面推荐“固定章节目录 + 主内容区”，窄屏转为可开合目录。内容宽度应适合长文阅读，代码块独立横向滚动。

#### 记忆点

只设置一个与主题相关的视觉记忆点，例如：

- 数据实验：可信结果证据链。
- 算法教程：状态如何逐步变化。
- 项目教程：代码模块如何连接为最终产物。

不要在所有区域同时使用动画、渐变、阴影和装饰。

### 第 5 步：编写教学内容

写作应面向学习者下一步要做什么。

- 先给结论，再解释原因。
- 每节解决一个问题，标题直接表达该问题。
- 用短段落、列表和表格降低认知负担，但避免过深嵌套。
- 首次出现的术语用普通语言解释。
- 说明关键选择的理由和主要取舍，而不只罗列 API。
- 把“易错点”放在对应步骤旁，而非全部堆到末尾。
- 示例值、预期输出和实际测试结果必须明确区分。
- 对不能确认的信息写明假设或限制。

代码教程中，每个关键片段至少解释：

1. 它负责什么。
2. 为什么在这里需要它。
3. 输入与输出是什么。
4. 哪个参数或结构最容易写错。

### 第 6 步：实现单文件 HTML

推荐结构：

```text
HTML
├── 阅读进度与跳转链接
├── 章节目录
├── 主题首屏
│   ├── 教程核心主张
│   ├── 学习成果
│   └── 全局图解
├── 快速概览
├── 若干学习章节
│   ├── 概念解释
│   ├── 图解与图注
│   ├── 分步说明
│   ├── 代码片段
│   └── 注意事项
├── 完整代码或完整方案
├── 运行与验证
├── 常见问题
└── 最终检查清单
└── 内置交互脚本
```

建议内置的轻量交互：

- 代码复制，Clipboard API 不可用时提供全选回退。
- 完整代码或文本模板下载，通过 Blob 生成，不依赖服务器。
- 章节目录当前位置高亮。
- 阅读进度。
- 可保存的检查清单，使用教程专属 localStorage 前缀。
- 移动端目录。
- 打印样式。

交互必须渐进增强：即使 JavaScript 失败，正文和完整代码仍应可读。

基础质量要求：

- 使用语义化标签和唯一标题层级。
- 所有内部锚点有效，ID 不重复。
- 键盘焦点清晰可见。
- 支持 `prefers-reduced-motion`。
- 代码块、表格和图解在窄屏不撑破页面。
- 不将真实密钥、个人隐私或内部凭据写入页面。

### 第 7 步：处理完整代码

若页面包含完整实现，必须把它视为正式交付物，而不是装饰性文本。

- 完整代码与拆解片段使用相同参数、路径和逻辑。
- 保留必要注释，解释关键约束和非显然决策，避免逐行复述。
- 不假设未确认的库或服务可用。
- 密钥通过环境变量或安全输入提供。
- 外部 API 不可用时，可以测试本地逻辑并模拟协议，但必须说明未做真实服务调用。
- 完整代码放在独立代码块中，并设置稳定 ID，便于提取验证和下载。
- HTML 中正确转义 `<`、`&` 等字符，下载时读取 `textContent` 还原源码。

对作业或验收型任务，额外做一次“显式要求 → 完整代码位置”的逐项核对，防止讲解正确但完整实现遗漏硬性要求。

### 第 8 步：验证内容与页面

不要只检查文件是否生成。

#### 内容验证

- 对照原始资料检查所有硬性要求。
- 检查数字、术语、链接和命令。
- 确认示意内容没有被写成真实结果。
- 检查注释和说明是否仍描述旧行为。

#### 代码验证

按代码类型选择实际可行的高强度验证：

1. 从 HTML 提取完整代码，确认提取内容完整。
2. 运行语法编译或解析检查。
3. 使用项目标准构建和测试命令。
4. 用临时数据执行核心端到端流程。
5. 验证生成物、错误路径和关键拒绝/边界行为。
6. 若涉及主循环或外部协议，使用可控模拟至少跑通一次完整消息序列。

测试产生的临时文件必须清理。不得为了通过验证而缩小原始要求。

#### HTML 与交互验证

- 使用 HTML 解析器检查结构、ID 和内部链接。
- 使用 JavaScript 语法检查。
- 在真实浏览器中检查渲染后的 DOM，确认脚本已初始化。
- 检查复制、下载、目录、清单等关键交互。

#### 视觉验证

至少检查：

- 常见桌面宽度。
- 窄屏布局。
- 长代码块和宽表格。
- 首屏标题是否出现孤字、溢出或异常换行。
- 图解是否清晰，文字是否被裁切。
- 打印时目录、按钮和代码是否合理。

若环境支持截图，生成临时截图并实际查看，再清理。注意某些桌面浏览器存在最小窗口宽度，不能把截图工具的裁切误判为页面横向溢出。

### 第 9 步：清理与交付

交付前：

- 删除截图、临时数据、测试产物和缓存。
- 不覆盖或删除用户原有文件。
- 若目录由版本控制管理，检查最终变更范围。
- 确认最终 HTML 独立打开时无网络依赖。

最终回复应简洁说明：

- 生成文件的可点击路径。
- 教程包含的核心内容。
- 已执行的验证。
- 仍需用户提供的真实配置或无法验证的外部条件。

## 五、质量门槛

只有全部满足以下适用项，才将教程视为完成：

### 学习性

- [ ] 读者能快速理解目标与最终成果。
- [ ] 章节顺序符合认知依赖，而非资料原文堆砌。
- [ ] 抽象结构至少有一种合适的图解表达。
- [ ] 关键概念解释“为什么”，不只解释“是什么”。
- [ ] 能通过练习、运行或清单检验学习成果。

### 正确性

- [ ] 所有显式要求已逐项闭环。
- [ ] 代码和命令经过与实际风险相称的验证。
- [ ] 完整实现与拆解说明一致。
- [ ] 示意输出与实际结果明确区分。
- [ ] 未验证的外部服务没有被宣称为已实测。

### 页面质量

- [ ] 单文件离线可用。
- [ ] 桌面与窄屏均可读。
- [ ] 代码、表格和图解无明显溢出。
- [ ] 内部导航和基础交互有效。
- [ ] 具备键盘焦点、减少动画和打印支持。

### 交付卫生

- [ ] 没有密钥或敏感信息。
- [ ] 没有遗留测试文件。
- [ ] 没有创建用户未要求的额外脚手架。
- [ ] 最终说明包含文件路径与验证边界。

## 六、常见失败模式

- **文档换皮**：只把 Markdown 放进 HTML，没有重新设计学习路径。
- **图解装饰化**：图很漂亮，但不能解释任何关系或流程。
- **片段与完整版不一致**：拆解代码能讲，完整代码却缺步骤或参数不同。
- **只看语法不跑流程**：代码能编译，但核心场景没有执行。
- **编造输出**：把预期值、示意值或模型生成值当成真实实验结果。
- **模板化视觉**：所有主题都使用相同配色、卡片和首屏数字。
- **交互过度**：动画和控件妨碍长文阅读，或脚本失败后正文不可用。
- **忽略硬约束**：页面内容完整，却漏掉原任务指定的结构、格式或验证方式。
- **测试残留**：最终目录混入截图、临时数据、日志和测试产物。

## 七、主题迁移方法

迁移到新主题时，保留流程，不照搬内容和视觉。

- **软件项目**：重点放在架构图、模块拆解、运行链路、测试与排错。
- **数据实验**：重点放在数据流、方法选择、指标解释、可复现性与证据链。
- **数学知识**：重点放在定义、直觉图、推导步骤、例题和常见误区。
- **历史或人文**：重点放在时间线、人物/事件关系、材料出处和多视角解释。
- **操作技能**：重点放在前置条件、分步图示、结果检查和故障恢复。

每次重新确定：学习者、核心成果、图解对象、视觉记忆点和验证方式。这样才能让同一技能适用于不同项目与知识点，而不是重复生成同一种页面。
